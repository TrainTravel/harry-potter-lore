# Python vs Scala: what each harness actually contains

The two implementations in this repo are not mirror images — they have
different scopes and different philosophies. This document captures the
actual state of each, and what each is uniquely good for.

## Surface area (what actually exists)

| Concern | Python | Scala |
|---|---|---|
| Domain types + errors | scattered across files | `Domain.scala` (one file, `DomainError` trait) |
| Context window w/ priority eviction | `context_manager.py` | `ContextAlgebra.scala` |
| RAG pipeline | `rag_pipeline.py` (chunking + retrieve + MMR) | `ContextPipeline.scala` (fs2 `Pipe` stages) + `VectorStore.scala` |
| Context assembly strategies | `context_assembler.py` (naive, relevance, sandwich, citation) | ❌ not ported |
| Prompt templates | `prompt_templates.py` | ❌ not ported |
| Async summarizer | `summarizer.py` | ❌ not ported |
| Document registry (stale-doc tracking) | `document_registry.py` | ❌ not ported |
| Cost tracking | `cost_tracker.py` | `CostTracker.scala` |
| Index version guard | `index_version_guard.py` | `IndexVersionGuard.scala` |
| Retrieval cache | `retrieval_cache.py` | `RetrievalCache.scala` |
| Tracing / observability | `tracer.py` (SQLite, OTel bridge, CLI viewer) | `TracerAlgebra.scala` (in-memory only) |
| Eval metrics | `evals/eval_agent.py` (LLM-as-judge) | `EvalMetricsAlgebra` (latency percentiles, not correctness) |
| Reliability (retry / breaker / bulkhead) | `reliability.py` | `ResilienceAlgebra.scala` |
| Security pipeline | `security.py` | ❌ not ported |

**Summary:** Python is the full stack (agent + evals + optimization +
infrastructure). Scala is the typed/streaming *core* of the
infrastructure — window, pipeline, cost, version guard, cache, retry,
trace — exposed as an HTTP service but without an agent or eval layer
on top.

## Philosophical differences (what's actually different about the code)

### Python style

- Classes with mutable state (`self._chunks`, `self._collection`).
- `asyncio` for async (`async def`, `await`, `asyncio.Task`).
- Duck-typed interfaces (protocols implicit).
- Errors by raising exceptions.
- Retrieval returns `List[Chunk]` — eager evaluation.
- Tests: pytest with in-memory ChromaDB.

### Scala style

- **Tagless-final** — every capability is a trait `Foo[F[_]]` with an
  `inMemory: IO[Foo[IO]]` interpreter. Business logic depends on the
  trait, not the implementation.
- **Cats Effect `IO`** instead of `asyncio` — pure effect values,
  composed with `for` / `flatMap`, run by an `IOApp`. Cancellation and
  backpressure are free.
- **fs2 streaming pipeline** — `ContextPipeline.run` is
  `scoreFilter andThen deduplicate andThen topK andThen assemble andThen inject`,
  each a `Pipe[IO, A, B]`. Lazy, back-pressured, composable.
- **`Ref[IO, State]`** instead of `self.x = ...` — explicit,
  thread-safe state cells.
- **Typed errors** — `DomainError extends Throwable` hierarchy
  (`IndexVersionMismatch`, `ContextBudgetExceeded`) vs Python's
  string-based exceptions.
- **`derives Encoder.AsObject, Decoder`** — JSON codecs generated by
  the compiler, no runtime reflection.

## Where the two converged (bug-for-bug)

The five deepTutor fixes (#2+#4, #3, #5, #6, #7) exist in both — that
was deliberate, to demonstrate the same ideas in two idioms:

- `cost_tracker.py` ↔ `CostTracker.scala` — same event schema, same
  rollup shape.
- `index_version_guard.py` ↔ `IndexVersionGuard.scala` — same
  `IndexManifest` JSON, same fail-fast semantics.
- `retrieval_cache.py` ↔ `RetrievalCache.scala` — both LRU+TTL, both
  targeted invalidation.
- `reliability.py` ↔ `ResilienceAlgebra.scala` — same three patterns
  (retry / circuit breaker / bulkhead).
- `tracer.py` ↔ `TracerAlgebra.scala` — same event kinds; Python
  persists to SQLite, Scala is in-memory only.

Fix #3 (async summarizer) only has a Python implementation because
the point was the Python asyncio-vs-user-turn blocking problem. In
Scala the equivalent is `IO.start(fa)` which is so trivial there's no
demo value.

## What's uniquely valuable in each

### Python gives you

- The **end-to-end agent** (from user question → answer → eval).
- DSPy compile loop.
- LLM-as-judge eval.
- A ChromaDB integration test that actually ingests and retrieves.

### Scala gives you

- The **HTTP service that actually boots** (`sbt run` → :8080 with
  `/ingest`, `/query`, `/health`, `/cost`, `/trace/{id}`).
- A reference implementation of each algebra that is *provably* total
  (types rule out the whole class of mistakes the Python version can
  still make at runtime).
- A way to see "same idea, different axis of rigor" — useful
  pedagogically for someone learning both paradigms.

## The honest assessment

If you had to pick one for a production tutor: **Python**. It has the
whole loop and the evals. Scala is ~40% of the surface area, running
as a demo.

If you had to pick one for *learning agent engineering patterns deeply*:
**read both side-by-side for the fixes that exist in both**. The Scala
version's types force the invariants into the signature (you literally
cannot forget to handle a `Ref`'s concurrent update); the Python
version lets you see the same invariant as a code convention you could
accidentally violate.
